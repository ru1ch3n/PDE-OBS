# Archived campaign results (index generated 2026-09-23 UTC, complete grid)

This directory is the machine-readable index of the archived runs behind the paper's 7 PDE x 7
method x 9 training-view grid, generated by `tools/archived_results.py` from the campaign runner's
own output records **without re-running anything**. Read [docs/archived_results.md](../../docs/archived_results.md)
first: it states the layout that was indexed, the checks, the cohort labels and what none of this
establishes.

## What is here

| File | Content |
|---|---|
| `index.json` | one record per identity (441): training cohort with its evidence, actual epochs, stop reason, checkpoint identity, resolved-configuration identity, registry / campaign / dataset identities, split receipt, health summary, the nine evaluation blocks (metrics, per-block file hash, mask protocol, observation ratio), every artifact hash |
| `checks.json` | the per-identity consistency checks (`blocks_complete`, `checkpoint_binding`, `metrics_file_binding`, `dataset_binding`, `split_provenance`, `training_completion`, `finiteness`, `metric_recomputation`) |
| `results_long.csv` | the long format of `docs/results_format.md`: one row per (identity, test view, metric); rollout rows also carry the per-horizon values |
| `matched_diagonal.csv` | the matched-view value (train view = test view) for all 441 planned identities; no cell is `RESULT_PENDING` |
| `cross_view/<pde>__<method>.csv` | the 9 x 9 (train view x test view) matrix per (PDE, method) |
| `pending.json` | empty: every planned identity has a completed evaluation |
| `summary.json` | the counts below |

## Read this before using a number

- **Scoring version.** These runs retained no prediction tensors, so every value is the campaign
  evaluator's stored `relative_l2` (the legacy relative-L2 family of `docs/results_format.md`), not a
  `pdeobs-strict-v1` block, and `scoring_version` says so on every row. Nothing here reaches the
  release's `paper-evaluated` evidence level as defined in `docs/claims_and_limits.md`, which requires
  the strict scorer with preserved scoring provenance.
- **Cohorts are not interchangeable.** 257 identities ran the original 500-epoch protocol to
  completion; 66 more reached 500 epochs after a recorded continuation; 36 completed a declared
  200-epoch budget after a continuation; 54 ran a budgeted max-200 patience protocol (44 with the
  epoch-120 floor, 10 without it); 28 are salvaged or user-terminated checkpoints evaluated before
  their budget was reached. Any table that pools cohorts must say so per row, which the long format does.
- **Epoch ceiling and stopping rule, declared per setting.** All 49 (PDE, method) pairs have all nine
  training views, so no cell is missing. Two epoch ceilings appear in the campaign: **500 epochs for 350
  settings and 200 for 91**. The ceiling is on every row as `planned_epochs` and what the run actually
  did is on every row as `actual_epochs`. A setting trains to its ceiling unless the training-data loss
  has already come down and further epochs move it very little; that is the only early-stopping rule
  (patience 10 on the training-data loss, with a 120-epoch floor in the `min120` variant), and the 20
  settings it stopped carry `stop_reason: train_data_patience_10`. A further 28 settings are evaluated
  from the last checkpoint written before their ceiling, and their epoch count is on the row. Every row
  also carries `training_cohort`, `checkpoint_id`, `resolved_config_identity`, `scoring_version` and
  `verification_status`, so the grid can be grouped or filtered from the file itself.
- **Evaluator identity.** 157 of the 441 records carry the frozen evaluator's SHA-256; 284 (every `original500`
  record and 27 salvaged ones) predate that field and read `legacy-campaign-evaluator:unrecorded`. That is a
  traceability limit, not evidence that those values are wrong.
- **Credit status.** The runner marked every one of these evaluations `preliminary`
  (`formal_credit: 0`); the acceptance policy it applied is recorded per identity in `index.json`.
- **What the checks mean.** `consistent` says that the nine blocks, the evaluation record, the
  training record and the split receipt of an identity agree on the checkpoint, the dataset, the
  identity set and the counts. It does not authenticate the data or the weights, does not recompute
  any metric, and does not compare anything to an independent reference.

## The ten identities added on 2026-09-23

The previous index stopped at 431 identities. Five of the ten that were missing had been recorded as
terminal failures: U-FNO on Poisson (block, boundary, clustered) and on Helmholtz (block, boundary)
collapsed to a constant output within the first few hundred optimizer steps in every bounded
learning-rate and gradient-clipping trial. They train normally under one setting change, a one-cycle
schedule at learning rate 5e-4 in place of the constant step schedule, and their matched relative-L2
values (0.040 to 0.068) sit inside the range of the rest of the grid. The other five finished their
budgeted or continued training in the ordinary way. All ten carry the same records, checks and
evaluator provenance as the rest of the index; their cohort labels say which protocol each one ran.

## Regenerating this directory

```bash
# on each machine that holds archives (read-only)
python tools/archived_results.py scan --training-root <root>/_preliminary-training/<campaign> \
  --evaluation-root <root>/_preliminary-evaluation/<campaign> --label <machine> --out ./scan-<machine>.json
# anywhere, with the scan files and the ledger-derived selection
python tools/archived_results.py pair --scan ./scan-*.json --selection ./selection.json --out ./paired.json
python tools/archived_results.py index --paired ./paired.json --out-dir ./results
```

The scan and pair files hold archive paths and are not committed; the selection file pins, per identity,
the SHA-256 of the evaluation record the campaign ledger credited. The runs themselves were not rerun
here: rescoring from retained arrays is unavailable because none were retained, and re-inference depends
on access to the checkpoints and data.
